# 深度分析框架
## 多维分析维度
对获取到的内容，从以下维度进行分析：
### 1. 核心价值提取
- **核心概念**：这个内容的关键思想/模式/算法是什么？
- **可复用性**：哪些部分可以被提取为通用能力？
- **独特性**：这些内容中有什么是 <占位-codex,claude code> 目前不具备的？
### 2. 适用场景映射
- **触发条件**：什么样的用户请求会需要这个知识？
- **使用频率**：这个能力会被多频繁地调用？
- **价值密度**：投入上下文窗口的 token 成本 vs 带来的价值
### 3. 与现有能力的关系
- **互补**：填补了哪些现有能力的空白？
- **重叠**：与哪些已有 Skill/规则有功能重叠？
- **冲突**：是否与现有规则/流程产生矛盾？
### 4. 消化形式评估矩阵
| 判断条件 | 建议形式 |
|----------|----------|
| 独立的多步骤工作流 + 复用频率高 | 新建 Skill |
| 单条行为约束或偏好 | 添加 rule |
| 已有 Skill 覆盖 ≥60% 功能 | 扩展已有 Skill |
| 需要确定性执行的脚本逻辑 | Skill 内 scripts/ |
| 领域知识/参考文档 | Skill 内 references/ |
| 模板/资源文件 | Skill 内 assets/ |
## 过滤规则 (When NOT to eat)
在分析完成后，必须过以下过滤器。命中任一条则拒绝消化，并向用户说明原因：
1. **一次性知识** — 查询型信息（"某 API 的参数是什么"），直接回答即可
2. **单行规则可解决** — 一条 rule 能搞定的，加到已有配置，不新建 Skill
3. **通用知识** — <占位-codex,claude code> 基础训练已覆盖的知识，无需重复存储
4. **高度重叠** — 已有 Skill 覆盖 ≥80% 功能时，应扩展已有 Skill 而非新建
5. **时效性内容** — 会快速过时的信息（某版本的 changelog），不适合固化
## 影响扫描清单
执行消化前，扫描以下位置：
```
~/.<占位-codex,claude code>/
├── skills/           → 检查每个 Skill 的 SKILL.md frontmatter
├── rules/            → 检查现有自定义规则
└── commands/         → 检查现有自定义命令
```
扫描要点：
- 列出所有与新内容有功能交集的已有 Skill
- 标注可能被影响的具体文件和段落
- 评估合并 vs 新建的利弊
