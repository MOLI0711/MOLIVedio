# 执行路径规划（后端）
## 路径选择规则
根据用户描述的任务复杂度和清晰度，选择最合适的执行路径：
| 路径 | 阶段 | 适用场景 |
|------|------|----------|
| **A** | userStory → design → taskList → coding | 需求模糊，描述不够清晰，需要从头澄清 |
| **B** | design → taskList → coding | 需求明确，但涉及复杂的技术决策（如数据库设计、接口设计、模块拆分） |
| **C** | taskList → coding | 需求和方案都清晰，只需要拆分任务直接开发（小功能、单模块改动） |
| **D** | coding | Bugfix 或极简改动，目标文件和修改点明确，可直接编码 |
## 判断标准
### 选择路径 A 的信号
- 用户描述含糊（"做一个 XXX 功能"，没有具体边界）
- 涉及多个业务域或外部系统集成
- 需要确认用户角色、权限、数据结构等核心概念
- 预计影响面广，需要前期对齐
### 选择路径 B 的信号
- 需求边界清晰，但技术方案需要设计（如新增微服务、重构模块）
- 需要明确 API 契约、数据库 Schema、缓存策略等
- 涉及跨团队接口，需要输出设计文档
### 选择路径 C 的信号
- 需求和技术方案都已经确定
- 改动范围小（单一模块、少量接口）
- 已有类似代码可参考，不需要新的架构决策
### 选择路径 D 的信号
- 明确的 Bug 修复（已知根因，已知修复方式）
- 配置变更、文案修改等极简改动
- 紧急热修复，需要最短路径
## 输出格式
输出以下格式的执行计划，然后使用 ask_followup_question 请求确认：
```
## 📋 执行计划
**需求**：{一句话描述用户的核心诉求}
**推荐路径**：{路径字母} — {路径阶段列表}
**推荐理由**：{1-2 句话说明为什么选择此路径}
---
请确认执行路径：
1. ✅ 确认路径 {推荐字母}：{推荐路径全称}
2. 改为路径 {备选1字母}：{备选1路径全称}
3. 改为路径 {备选2字母}：{备选2路径全称}
4. 其他调整（请说明）
```
## 扩展说明
> 💡 **业务定制提示**：
> 可以在此文件中增加业务专属路径，例如：
> - **E**：数据库迁移 → taskList → coding（仅涉及 DB Schema 变更）
> - **F**：文档更新 → 仅修改文档，不涉及代码
> - **G**：配置发布 → 仅修改配置项
>
> 增加路径后，同步更新"路径选择规则"和"判断标准"部分。
