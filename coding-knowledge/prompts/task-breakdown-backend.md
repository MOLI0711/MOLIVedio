# 任务拆分阶段（后端）
## 核心目标
将技术方案拆解为可并行、可验收、可执行的任务清单。
## 交互流程
### 输出规范（强约束）
- 默认不输出完整示例代码/可运行 Demo/大段 SQL。
- 如必须举例：每步最多 1 段，≤ 10 行，仅保留关键逻辑（优先伪代码/JSON/字段表）。
- 只有用户明确要求“给代码/给示例实现”时才扩展输出。
### Step 1: 理解技术方案
**输出内容**：
- 需求项和技术方案要点总结
- 涉及的技术组件：数据库、缓存、MQ、RPC 等
- 疑问（如有）
✋ **等待用户确认**
---
### Step 2: 确定任务结构
**输出内容**：
- **Phase 划分**（建议分层推进）：
  - Phase 1: 数据层（DB Schema、数据迁移）
  - Phase 2: 基础设施（缓存、MQ、配置）
  - Phase 3: 核心逻辑（Service、Repository）
  - Phase 4: 接口层（Controller、DTO）
  - Phase 5: 测试与优化（单测、集成测试、性能优化）
- **每个 Phase 的目标和预计任务数**
✋ **等待用户确认结构**
---
### Step 3: 拆解各阶段任务（逐个 Phase 确认）
⚠️ **一次只拆解一个 Phase**
**输出内容**（针对单个 Phase）：
- **任务列表**：
| 任务编号 | 任务描述 | 涉及文件 | 可并行 | 预计工时 |
|---------|---------|---------|--------|---------|
| T1.1 | 创建 xxx 表 | xxx.sql | - | 0.5d |
| T1.2 | 添加索引 | xxx.sql | [P] | 0.5d |
- **检查点**：此 Phase 完成后如何验证
**拆分原则**：
- 数据库任务：一个表/索引 = 一个任务
- 缓存任务：一个 Key 设计 = 一个任务
- 接口任务：一个 API = 一个任务
- 粒度：0.5-2 天工作量
✋ **确认本 Phase 后再继续下一个**
---
### Step 4: 确认依赖和执行顺序
**输出内容**：
- **Phase 间依赖关系**：
  ```
  Phase 1 (数据层)
    |
  Phase 2 (基础设施) + Phase 3 (核心逻辑) [可并行]
    |
  Phase 4 (接口层)
    |
  Phase 5 (测试优化)
  ```
- **任务级依赖**（如有复杂依赖）
- **推荐执行顺序**
- **可并行任务标识** [P]
✋ **等待用户确认**
---
### Step 5: 整合任务清单
**输出内容**：
生成完整的 `task.md` 文档，包含：
1. 任务结构（Phase 划分）
2. 详细任务列表（每个 Phase 的任务）
3. 依赖关系图
4. 执行顺序建议
5. 总预计工时
**保存路径**：`.<占位-codex,claude code>-spec/specs/{功能名}/task.md`
---
## 任务拆分原则
- **最小化依赖**：任务之间依赖最少
- **最大化并行**：尽可能让任务可并行执行
- **独立验收**：每个任务可独立验收（单测、集成测试）
- **合理粒度**：单个任务 0.5-2 天工作量
- **分层推进**：数据层 → 逻辑层 → 接口层
## 粒度参考
✅ **好的粒度**：
- 一个任务 = 一个明确的交付物（一个接口、一个表、一个缓存设计）
- 一个任务 = 一个可独立测试的单元
❌ **需要拆分**：
- 任务涉及多个文件、多个功能点
- 任务跨多层（数据层+逻辑层+接口层）
✅ **可以合并**：
- 任务只改几行代码
- 多个小改动在同一个文件
